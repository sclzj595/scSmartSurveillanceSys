# 智能安防监控系统产品需求文档（PRD）

**文档版本：** V2.2  
**文档状态：** 开发基线评审版  
**更新日期：** 2026-10-17  
**产品类型：** Windows 桌面端智能安防监控软件  
**核心技术：** Qt / C++ / OpenCV  
**当前开发阶段：** S1 单机安防闭环  
**产品定位：** 面向店铺、工作室、家庭门口等小微场景的本地实时视频监控、视觉识别、异常告警与事件追溯工具。

---

## 1. 产品概述

### 1.1 产品背景

现有系统基于 Qt、C++ 和 OpenCV 实现，已具备单路 USB 摄像头预览、人脸检测与识别、遗留物检测、禁区入侵判定等基础能力，并已完成采集、分析和画面渲染的异步化改造。

当前产品需要从能够运行的技术原型，逐步完善为可以稳定操作、持续运行、可靠留存事件的桌面安防软件。

当前重点不是继续堆叠识别算法，而是解决实时性、识别可信度、业务完整性、设备异常恢复、事件存证和交互反馈等问题。

### 1.2 产品目标

本系统围绕四项核心能力建设：

1. **实时监控：** 持续显示摄像头最新画面，避免因分析线程阻塞或消息积压导致延迟累积。
2. **智能识别：** 对人员身份、陌生人、禁区入侵和遗留物进行检测与规则判定。
3. **告警与存证：** 将有效识别结果转换为统一事件，保存事件信息和对应截图，支持历史查询。
4. **本地化管理：** 持久化人员档案、禁区配置和系统设置，提供设备状态反馈、异常恢复与数据删除能力。

### 1.3 产品成功标准

| 指标 | 验收要求 |
|---|---|
| 视频预览 | 720p 条件下目标渲染帧率不低于 24 FPS，波动目标为 ±2 FPS |
| 视频帧龄 | 正常运行时不超过 250 ms |
| 识别调度 | 满足每秒至少 10 次分析的目标，实际能力以算法耗时和硬件测试为准 |
| 运行稳定性 | 完成 2 小时性能专项测试及 24 小时长稳验收 |
| 人脸档案 | 注册后重启软件，档案与样本仍可用 |
| 禁区判定 | 窗口缩放、留边变化后，绘制区域与判定区域保持一致 |
| 事件追溯 | 事件可持久化查询，启用截图存证时能够查看对应截图 |
| 设备异常 | 摄像头断开、占用和恢复均有明确状态与处理路径 |
| 数据隐私 | 人脸数据默认仅在本机保存，提供明确告知与删除能力 |

上述为产品目标，不代表所有指标目前已经通过验收。帧率、帧龄、分析耗时及长稳结果应分别记录实际测试值。

### 1.4 本期产品边界

本期以 Windows 桌面端单机运行作为交付目标。

- 默认场景：单路 USB 摄像头。
- 数据处理：本地采集、本地分析、本地存储。
- 用户模式：单管理员操作员，无账户体系。
- 核心闭环：视频采集 → 视觉分析 → 规则判定 → 画面标注 → 事件记录 → 截图存证 → 历史查询。
- 服务通信：仅对已经实现的本地服务能力提供操作入口和状态反馈。

RTSP、多路摄像头、手机端远程查看、远程控制、门锁联动及运动相机接入均不属于当前阶段的验收前提。

## 2. 用户角色与使用场景

### 2.1 用户角色

| 角色 | 职责 | 核心需求 |
|---|---|---|
| 操作员 | 启动监控、设置识别规则、管理人脸、查看告警 | 画面实时、操作明确、事件可信 |
| 被拍摄者 | 出现在摄像头视野中的人员 | 知情、隐私保护、数据可删除 |

本期不建立多用户账户、角色权限和远程访客体系。

### 2.2 核心使用场景

**场景 A：日常实时监控**

操作员打开软件，系统连接摄像头并展示实时画面。操作员可以开启或关闭人脸识别、遗留物检测等功能，随时了解视频源与识别服务状态。

**场景 B：已注册人员识别**

操作员在获得必要知情同意后注册人员档案。此后系统根据当前画面中的人脸与本地档案进行比对，在符合判定条件时显示人员名称和相似度，并按照事件冷却规则记录识别事件。

**场景 C：陌生人告警**

当画面中出现满足检测条件、但未能匹配本地档案的人脸时，系统显示陌生人标注。相同目标在冷却窗口内不重复生成相同类型事件。

**场景 D：禁区入侵**

操作员在视频画面上绘制禁区。目标进入禁区并达到规定的面积重叠比例后，系统显示入侵标注、产生告警并尝试保存截图。

**场景 E：遗留物监测**

操作员手动开启遗留物检测并配置持续时间阈值。符合规则的静止目标被确认后生成遗留物事件；目标移除后生成解除事件。

**场景 F：事件追溯**

操作员进入历史记录，按时间和事件类型筛选记录，查看事件详情与截图，确认发生时间和事件内容。

**场景 G：设备异常恢复**

摄像头被拔出、占用或发生断流时，界面明确显示异常状态；系统按重连策略恢复连接，并在恢复后使用最新帧继续预览。

| 人脸识别 | 人脸检测、本地档案比对、陌生人判定 |
| 人员档案 | 注册、追加样本、删除、重启恢复 |
| 禁区管理 | 绘制、预览、清除、坐标映射、持久化 |
| 遗留物检测 | 手动启用、持续时间判定、移除事件 |
| 事件中心 | 统一事件模型、事件列表、详情、筛选 |
| 截图存证 | 事件截图保存、路径管理、失败反馈 |
| 标注系统 | 统一颜色、框体、标签、中文显示 |
| 设置管理 | 主题、识别阈值、告警声音、诊断信息等设置持久化 |

### 3.2 P1：核心闭环完成后的增强

- 完善设备状态机与自动恢复。
- 优化历史记录检索、详情展示和留存清理。
- 增强识别规则可配置性及误报诊断。
- 完善本地服务状态、推流状态和错误提示。
- 统一 UI 交互细节、键盘操作、空状态与异常状态。
- 在满足独立验收条件后，开展单路 RTSP 接入。

### 3.3 P2：后续扩展方向

- 多路摄像头及通道管理。
- 移动端事件接收与远程控制。
- 远程实时视频传输。
- 运动相机 SDK 接入。
- 授权门锁联动与开门事件审计。

P2 不得反向扩大当前版本的交付范围。

## 4. 总体架构与模块职责

### 4.1 逻辑架构

系统采用桌面应用内的分层模块设计，当前不要求拆分为多个独立服务进程。

**客户端与交互层**

- 主窗口与实时视频面板。
- 人员注册与档案管理界面。
- 禁区绘制与规则设置界面。
- 事件中心、历史记录与详情窗口。
- 系统设置、设备状态和诊断展示。

**安防业务层**

- 人员档案管理。
- 禁区配置及入侵判定。
- 遗留物状态管理。
- 事件生成、冷却、归档及删除。
- 告警通知与截图存证协调。
- 本地隐私数据管理。

**视觉引擎层**

- 视频帧获取与最新帧调度。
- 人脸检测与识别。
- 运动目标分析与跟踪。
- 结构化分析结果输出。
- 预览标注与诊断数据。

**设备接入层**

- 当前 USB 摄像头适配。
- 统一的视频源控制接口。
- 后续 RTSP 和其他视频源适配。

**本地数据层**

- 人员档案与人脸特征。
- 系统配置与禁区配置。
- 事件元数据。
- 事件截图。
- 运行日志及必要的操作记录。

### 4.2 模块边界

1. 采集线程只负责取流及最新帧更新，不执行重型识别。
2. 分析线程只输出结构化结果，不直接操作 GUI 控件。
3. GUI 线程负责预览绘制、标注叠加和用户交互，不执行耗时识别。
4. 视觉引擎不直接决定安防业务事件是否成立。
5. 安防业务层统一判定事件、冷却规则和事件生命周期。
6. UI 不直接依赖人脸库文件内部格式，应通过档案业务接口读写。
7. 截图和事件元数据必须保持关联，但存储失败不得反向阻塞视频预览。
8. 设备控制、服务状态与识别状态必须分别维护，不得用一个“运行中”状态代替所有状态。

### 4.3 统一数据契约

视觉分析结果至少包含：

- 帧序号或可追踪的帧标识。
- 采集时间或可计算帧龄的时间信息。
- 人脸检测框、识别名称、相似度、是否命中档案。
- 目标框、跟踪标识及遗留物确认状态。
- 分析耗时、分析频率和异常状态。

安防业务事件至少包含：

- 事件 ID。
- 事件类型。
- 发生时间。
- 视频源标识。
- 关联人员或目标信息。
- 事件截图引用及存储状态。
- 事件状态与必要的错误信息。

字段可以根据现有代码模型调整，但必须保持引擎输出、业务判定、UI 展示和持久化之间的语义一致。

## 5. 实时视频与设备管理

### 5.1 视频处理管线

当前采用以下处理方式：

摄像头采集线程 → FrameBank 最新帧槽 → 分析线程 → 结构化分析结果 → GUI 渲染节拍 → 视频显示控件。

核心规则：

- FrameBank 采用覆盖式最新帧语义，不积累历史待处理帧。
- 分析线程按实际耗时进行节流与跳帧。
- GUI 按独立节拍获取最新帧并绘制。
- 每次绘制均使用独立图像副本，避免修改共享图像。
- 没有新帧时不得重复执行重型分析。
- 暂停恢复时不回放暂停期间积压的旧帧。
- 单帧分析异常不得导致整个应用退出。

### 5.2 性能指标

| 指标 | 目标 | 测试方法 |
|---|---|---|
| 采集帧率 | 720p 条件下目标 ≥25 FPS | 记录设备实际交付帧率 |
| 渲染帧率 | ≥24 FPS，波动目标 ±2 FPS | 连续采样并统计平均值、最低值和波动 |
| 分析频率 | ≥10 Hz | 统计单位时间内完成的分析次数 |
| 分析耗时 | P95 ≤120 ms | 记录单帧耗时分布 |
| 帧龄 | ≤250 ms | 通过采集时间戳与显示时间测量 |
| 队列积压 | 最新帧槽不形成历史帧队列 | 代码检查及压力测试 |
| 短时稳定性 | 2 小时运行无明显指标漂移 | 记录帧率、帧龄、内存及异常 |
| 长时稳定性 | 24 小时无人值守运行 | 检查进程存活、设备状态和事件完整性 |

以上指标受摄像头能力、驱动、分辨率、光照和 CPU 性能影响。测试报告必须记录实际设备、构建类型、分辨率及识别开关状态。

### 5.3 视频源操作

主界面应提供：

- 当前视频源名称。
- 当前连接状态。
- 可用设备切换入口。
- 暂停与恢复操作。
- 视频源切换后的连接反馈。
- 无设备时的空态说明。
- 摄像头被占用或断流时的错误提示。

默认请求 1280×720、30 FPS。设备不支持时，选择其可用的接近档位，并在诊断信息中显示实际参数。

### 5.4 设备状态机

| 状态 | 触发条件 | 界面反馈 |
|---|---|---|
| 未连接 | 启动时无设备或连接失败 | 显示空态和重试入口 |
| 连接中 | 开始打开设备 | 显示连接中状态 |
| 在线 | 取流成功 | 正常预览及绿色状态 |
| 重连中 | 设备断开或取流失败 | 显示断流提示及重试状态 |
| 异常终止 | 达到连续失败次数 | 显示明确错误并产生源离线事件 |

连接尝试超时目标为 3 秒。重连策略采用递增等待，最大间隔 30 秒；连续 5 次失败后进入未连接状态。

设备恢复后必须清除过期帧，并从最新画面恢复。

### 5.5 暂停、关闭和退出

- 暂停期间，画面可以冻结，但必须显示“已暂停”标识。
- 恢复时清除过期帧，不回放旧画面。
- 关闭识别不应导致视频预览停止。
- 关闭窗口或退出程序时，应停止采集、等待线程退出并释放摄像头。
- 不允许 GUI 线程与采集线程同时释放或操作同一视频设备对象。

## 6. 人脸识别与人员档案

### 6.1 人脸检测与识别

当前基线使用 HAAR 级联检测和独立 FaceAlgorithm 组件中的 LBPH 网格直方图识别能力。

处理流程：

1. 检测当前帧中的人脸。
2. 过滤尺寸不符合要求的人脸。
3. 对有效人脸提取与训练过程一致的特征描述。
4. 与本地人员档案进行比对。
5. 输出识别名称、相似度和命中状态。
6. 交由安防业务层判断是否产生事件。
7. 由渲染层统一显示标注。

人脸短边小于 60 px 时，不参与识别。注册人脸同样要求满足最小尺寸。

### 6.2 识别开关

- 默认关闭。
- 用户开启后开始执行人脸识别。
- 关闭识别时保留实时预览。
- 开关状态必须在界面上有明确反馈。
- 如果档案库为空，应提示尚未注册人员，并允许继续执行陌生人检测。
- 识别失败时应区分无人脸、质量不合格、无匹配结果和算法异常。

“识别开启”只代表算法正在执行，不代表当前画面一定识别成功。

### 6.3 相似度与阈值

对外相似度统一使用 0–100% 的百分比表示，数值越高代表当前算法定义下的匹配程度越高。

- 无有效结果时显示“—”。
- 内部距离、异常浮点数、无效值不得直接显示。
- 默认阈值可暂设为 55%–60% 的待标定基线，最终默认值由实际同人、异人样本测试确定。
- 允许操作员在限定范围内调整阈值。
- 阈值变化应立即生效，并持久化保存。
- 修改相似度映射公式时，必须同步验证数据和阈值。

**重要约束：** 当前算法输出的相似度不能直接等同于真实身份概率。界面和文档不得将“92% 相似度”描述为“92% 概率确认是此人”。

### 6.4 人员注册

入口：主界面的“注册人脸”按钮。

交互流程：

1. 检查当前视频源是否在线。
2. 异步检测当前画面中最大的人脸。
3. 无人脸、尺寸过小或图像质量不满足要求时，显示具体原因。
4. 检测成功后弹出注册窗口。
5. 展示人脸预览和姓名输入框。
6. 用户确认后执行入库与训练。
7. 成功后提示注册完成，并更新人员档案列表。

注册操作必须异步执行，不得长时间阻塞 GUI。

同名注册视为追加样本，不重复创建人员档案。新增样本必须经过尺寸和有效性校验。

### 6.5 人员档案管理

档案字段至少包括：

- 档案 ID。
- 人员名称。
- 样本数量。
- 创建时间及最近更新时间。
- 档案状态。

支持能力：

- 查看档案列表。
- 查看单个档案的基本信息。
- 追加人脸样本。
- 删除指定档案。
- 重启后恢复档案。
- 清除全部人脸档案和生物特征数据。

删除档案时需二次确认，并清理与该档案关联的人脸样本和特征数据。

### 6.6 并发与异常约束

- 同一分类器不得在不受保护的情况下并发执行检测。
- 训练和预测必须使用一致的特征描述方式。
- 单帧算法异常仅影响当前帧，不得终止整个程序。
- 注册过程应避免读取正在被后续采集修改的图像。
- 档案持久化失败时必须反馈失败，不能只提示注册成功。
- 档案写入应避免程序异常退出导致旧数据损坏。

## 7. 禁区与遗留物检测

### 7.1 禁区管理

禁区是操作员在视频画面中设置的矩形监控区域。

操作入口：点击“设置禁区”进入绘制模式，再次点击退出；提供清除禁区的入口。

功能要求：

- 鼠标拖拽绘制矩形。
- 绘制时显示实时预览。
- 支持清除现有禁区。
- 支持启用和停用禁区规则。
- 禁区配置重启后恢复。
- 窗口缩放、视频留边和分辨率变化后，禁区仍然映射到正确的源帧位置。

### 7.2 坐标映射

所有视频交互统一遵循等比缩放与居中留边规则。

- 源帧坐标用于业务判定与持久化。
- 显示坐标仅用于屏幕绘制和鼠标交互。
- 鼠标绘制坐标必须转换到源帧坐标。
- 检测框必须经过同一映射规则转换后绘制。
- 禁止在不同模块中重复实现各自的坐标换算。

### 7.3 入侵判定

当目标进入禁区，且目标框与禁区框的交集面积占目标框面积达到或超过 30% 时，判定为入侵。

入侵后：

- 显示红色高亮标注。
- 产生入侵事件。
- 按规则执行告警声音。
- 保存对应截图。
- 同一目标在 10 秒冷却窗口内不重复产生相同类型事件。

禁区绘制状态与实际入侵状态必须区分。禁区框长期存在不代表当前发生了入侵。

### 7.4 遗留物检测

遗留物检测默认关闭，由操作员手动启用。

默认持续时间阈值为 60 秒，支持在规定范围内调整。

处理流程：

1. 检测并跟踪运动或静止目标。
2. 记录目标持续存在时间。
3. 排除小面积噪点和不符合条件的目标。
4. 目标满足遗留物规则后，生成遗留物事件。
5. 目标被移除后，生成遗留物解除事件。

标注规范：

- 普通跟踪目标使用灰色细框。
- 已确认遗留物使用琥珀色实线框。
- 遗留物标签显示持续时间。
- 不得把所有运动目标或背景建模区域都显示为遗留物告警。

## 8. 统一事件与告警中心

### 8.1 事件类型

| 类型 | 触发条件 | 冷却规则 |
|---|---|---|
| 人员识别 | 有效识别结果命中人员档案 | 同目标 30 秒 |
| 陌生人出现 | 满足条件但未匹配人员档案 | 同目标 30 秒 |
| 遗留物确认 | 目标持续存在并满足遗留物规则 | 不使用重复冷却替代状态判断 |
| 遗留物解除 | 已确认遗留物被移除 | 不冷却 |
| 禁区入侵 | 目标与禁区重叠比例达到阈值 | 同目标 10 秒 |
| 视频源离线 | 视频源达到离线判定条件 | 按状态转换生成 |
| 视频源恢复 | 视频源从异常状态恢复在线 | 按状态转换生成 |

同一事件类型、同一目标在冷却窗口内重复触发时，应合并或抑制重复事件，但不能因此关闭实时标注。

### 8.2 事件字段

每条事件至少保存：

| 字段 | 说明 |
|---|---|
| eventId | 全局唯一事件标识 |
| type | 事件类型 |
| occurredAt | 事件发生时间 |
| sourceId | 视频源标识 |
| targetId | 关联目标标识，可为空 |
| personId | 关联人员档案，可为空 |
| summary | 事件摘要 |
| snapshotPath | 截图路径，可为空 |
| snapshotStatus | 待保存、成功、失败或未启用 |
| status | 活跃、归档或已删除 |
| createdAt | 事件持久化时间 |

事件发生时间与事件保存时间必须区分，避免截图写入延迟导致时间展示错误。

### 8.3 实时告警

实时告警通过以下方式呈现：

- 视频画面标注。
- 主界面事件日志。
- 事件中心未读数量。
- 可配置的声音提示。
- 视频源异常横幅。

告警提示与事件记录属于不同层次：提示可以被查看或消退，但事件记录必须按持久化规则保存。

### 8.4 事件中心

事件中心提供：

- 按时间倒序排列。
- 按事件类型筛选。
- 查看事件详情。
- 查看原始存证截图。
- 显示事件发生时间、类型、关联人员或目标。
- 显示截图保存失败状态。
- 删除事件前进行二次确认。
- 显示当前筛选结果数量及空状态。

建议支持按日期范围筛选，但可在核心事件持久化完成后实施。

### 8.5 事件生命周期

事件状态：

- 活跃：刚触发并需要重点提示。
- 归档：事件仍然可查询，但不再持续高亮。
- 已删除：用户确认删除后进入终态。

活跃事件可在 24 小时后自动归档。

删除事件时，应按照产品隐私与存证规则处理关联截图，避免删除元数据后留下无法管理的孤立文件。

### 8.6 截图存证

默认开启事件截图存证。

截图要求：

- 在事件触发时保存对应画面。
- 画面包含与该事件对应的标注。
- 保存成功后记录截图路径。
- 截图写入失败时显示明确提示，并记录失败原因。
- 磁盘空间不足或目录不可写时，不得阻塞实时预览。
- 截图设置关闭后，事件仍需记录，只是不生成截图文件。

建议目录结构：

`events/YYYY-MM-DD/HHmmss_eventType_eventId.png`

采用事件 ID 防止同一秒内多条事件产生文件名冲突。

### 8.7 历史数据留存

初始设计目标为本地事件与截图按 30 天留存，最终期限需在设置和隐私说明中统一。

清理机制必须满足：

- 仅清理超过留存期限且符合清理条件的数据。
- 不删除仍被有效事件引用的文件。
- 删除失败时记录日志。
- 清理过程不得阻塞视频预览。
- 提供必要的磁盘空间与存储失败提示。

## 9. 主界面与交互规范

### 9.1 当前界面评审

当前截图已经具备视频主区域、状态栏、检测标注和快捷操作入口，整体方向正确：视频区域占据主要空间，深色视频底可以突出画面内容。

但从现有截图可以观察到几个值得优先处理的问题：

**问题一：状态信息不够清晰。**

顶部显示 USB 源正常、服务未启动，但二者的关系不明确。操作员需要知道服务未启动具体影响什么能力，而不是只看到红色状态。

**问题二：检测标注竞争画面。**

当前红色入侵框范围较大，与人脸识别框、禁区框和顶部信息相互接近。应明确区分“禁区范围”“入侵目标”和“人脸识别目标”，避免不同对象看起来像同一个框。

**问题三：诊断信息与告警信息需要分区。**

FPS、分析频率、帧龄等诊断数据不应和业务告警争夺视觉焦点。应采用稳定位置、较低视觉权重的诊断区；告警发生时再突出告警信息。

**问题四：底部异常信息过于技术化。**

当前截图保存失败时直接显示文件路径，开发调试有用，但不适合作为唯一反馈。应同时显示简短、可理解的提示，并允许用户查看详细错误。

**问题五：操作入口需要明确主次。**

人脸识别、设置禁区、注册人脸、历史记录和推流属于不同类别，应分组呈现，减少按钮之间的视觉竞争。

以上是基于当前截图的 UI 观察，不代表所有相关功能的内部实现均存在问题。

### 9.2 主窗口布局

建议将主窗口划分为五个区域。

**A. 顶部状态栏**

- 产品名称与图标。
- 视频源状态。
- 识别服务或推流服务状态。
- 当前主题入口。
- 必要的系统状态提示。

**B. 实时视频主区域**

- 默认使用等比缩放。
- 黑色留边。
- 视频内容优先。
- 检测框与告警标注直接叠加。
- 无视频时展示明确的空态。
- 断流时冻结最后一帧，并叠加明显的断流提示，禁止让用户误以为画面仍然实时。

**C. 视频诊断区**

展示预览 FPS、分析 Hz、单帧分析耗时和帧龄。诊断区可关闭，默认开启。

**D. 主操作区**

按功能分组：

- 识别控制：人脸识别、遗留物检测。
- 规则设置：设置禁区、清除禁区。
- 人员管理：注册人脸、人员档案。
- 事件管理：历史记录、事件中心。
- 视频控制：暂停、恢复、设备切换。
- 扩展能力：WebRTC 推流，仅在对应服务能力可用时提供明确状态。

**E. 底部状态与反馈区**

- 当前操作结果。
- 最近一条告警摘要。
- 设备异常与截图存储错误。
- 详细日志入口。

底部区域不得长期展示大量不可读的内部路径和调试文本。

### 9.3 标注视觉规范

| 语义 | 样式 | 标签 |
|---|---|---|
| 已识别人脸 | 绿色角括号或实线框 | 人员名称 + 相似度 |
| 陌生人 | 黄色角括号或实线框 | 陌生人 |
| 跟踪目标 | 灰色细框 | 默认不显示文字 |
| 已确认遗留物 | 琥珀色实线框 | 遗留物 + 持续时间 |
| 禁区 | 红色闭合虚线框 | 禁区 |
| 入侵目标 | 红色加粗框 | 入侵 |

规则：

- 颜色必须具有稳定语义。
- 不得将内部浮点数直接渲染到视频上。
- 标签必须有半透明底，保证复杂画面中的可读性。
- 标签不能遮挡人脸关键区域。
- 多个框重叠时，应优先展示告警信息，但不能因此改变检测数据。
- 诊断信息不应覆盖禁区标签或入侵告警。
- 标注绘制与业务判定使用同一坐标映射规则。

### 9.4 交互状态规范

所有按钮必须具备明确的状态：

- 默认。
- 悬停。
- 按下。
- 禁用。
- 已开启。
- 临时模式选中。

持续生效的开关和临时交互模式必须使用不同的状态表达。

例如，人脸识别开启属于持续状态；禁区绘制属于临时模式。二者不能仅通过相同颜色或相同文字表示。

### 9.5 主题与设计令牌

沿用当前 DesignTokens 设计体系，作为全局样式的唯一事实来源。

- 深色主题为默认主题。
- 浅色主题作为可选主题。
- 视频区域始终保持黑色背景。
- 界面框架使用低饱和背景和细分隔线。
- 绿色表示正常或识别命中。
- 琥珀色表示警示或临时操作。
- 红色表示告警或异常。
- 蓝色表示焦点与选中状态。

颜色、圆角、间距、字体和组件状态统一由设计令牌管理。业务代码不得随意散落十六进制颜色。

## 10. 系统设置与持久化

### 10.1 设置项

| 设置项 | 默认值 | 生效方式 |
|---|---|---|
| 主题 | 深色 | 即时生效 |
| 视频源 | 系统默认设备 | 切换后重连 |
| 人脸识别 | 关闭 | 即时生效 |
| 人脸相似度阈值 | 待标定默认值 | 即时生效 |
| 遗留物检测 | 关闭 | 即时生效 |
| 遗留物持续时间 | 60 秒 | 即时生效 |
| 禁区配置 | 无或上次保存值 | 保存后持久化 |
| 告警声音 | 开 | 即时生效 |
| 诊断信息显示 | 开 | 即时生效 |
| 事件截图存证 | 开 | 即时生效 |
| 事件留存时间 | 建议 30 天 | 定期清理 |

### 10.2 持久化原则

- 设置文件不依赖程序启动时的工作目录。
- 人脸档案、事件元数据和截图均使用统一的数据目录管理策略。
- 保存成功后才能向用户反馈成功。
- 设置文件损坏时应提供恢复或重置路径。
- 不能因单个设置读取失败导致整个应用无法启动。
- 用户重启后，档案、禁区和设置必须恢复到最后一次成功保存的状态。

### 10.3 数据目录

统一使用应用数据目录配置，避免通过相对路径写入不可预测的位置。

数据目录至少包含：

- `config/`：系统配置。
- `faces/`：人员档案与人脸数据。
- `events/`：事件截图。
- `logs/`：运行日志。

具体目录名称可按当前代码结构调整，但所有模块必须使用统一路径管理接口，不得各自拼接不同的根目录。

## 11. 隐私与数据安全

### 11.1 人脸数据告知

首次注册人脸前，必须明确告知：

- 将采集的人脸图像及特征数据类型。
- 数据保存于本机。
- 数据用途为本地人员识别。
- 数据不会因本地识别功能而默认上传至云端。
- 如何删除单个人员档案及全部生物数据。

用户未确认前不得开始入库。

### 11.2 本地化原则

当前版本的人脸数据、人员档案、事件记录和截图默认仅在本机存储。

若启用后续网络视频源或远程功能，必须重新界定网络通信范围。不得将“支持 RTSP 拉流”等同于“允许上传人脸数据”。

### 11.3 删除规则

- 删除人员档案时清除对应人脸样本与特征。
- 清除全部生物数据前二次确认。
- 删除操作应检查文件和元数据的清理结果。
- 对于无法删除的文件，提示失败并记录必要的错误信息。
- 事件截图的删除遵循事件与存证的关联规则。

### 11.4 日志约束

日志可记录错误类型、时间、模块和必要的诊断信息，但不得记录人脸图像本体或不必要的敏感信息。

### 11.5 隐私说明

交付时提供简版隐私说明，描述本地处理方式、采集用途、数据位置、删除操作及网络通信边界。涉及实际部署或对外提供服务时，应进一步核验适用的法律法规及告知同意要求。

## 12. 服务状态与 WebRTC 推流

### 12.1 能力定位

当前界面已提供 WebRTC 推流入口，并显示服务状态。该能力应与本地 USB 视频预览及人脸识别状态明确区分。

本期不以远程视频一定成功为核心验收条件，但界面必须准确反馈实际服务状态，不能使用固定文案或仅凭按钮点击状态推断服务已启动。

### 12.2 状态要求

至少区分：

- 服务未启动。
- 服务启动中。
- 服务已启动。
- 服务异常。
- 推流未开启。
- 推流连接中。
- 推流正常。
- 推流中断。

只有实际确认服务状态后，才能显示“已启动”或“推流正常”。

### 12.3 异常处理

- 服务启动失败时，显示简短原因及重试入口。
- 推流失败不得影响本地视频预览。
- 推流停止后应及时更新界面状态。
- 服务状态与 USB 摄像头状态分别维护。
- 详细技术错误放入可查看的诊断日志，不直接覆盖主画面。

远程视频所需的信令、媒体通道、连接鉴权和网络环境要求，须在后续专项设计中单独定义。

## 13. 异常处理与运行日志

### 13.1 异常场景

| 异常 | 处理要求 |
|---|---|
| 无摄像头 | 显示空态，禁用依赖视频的操作 |
| 摄像头被占用 | 显示原因并定时重试 |
| 摄像头拔出 | 显示断流状态并启动重连 |
| 人脸检测失败 | 记录错误，当前帧跳过，不退出程序 |
| 人脸注册失败 | 显示原因，恢复按钮状态 |
| 档案保存失败 | 不得提示注册成功 |
| 截图保存失败 | 事件保留，截图状态显示失败 |
| 磁盘空间不足 | 提示存储异常，不阻塞视频预览 |
| 设置文件损坏 | 提示并提供恢复默认值的路径 |
| 服务启动失败 | 显示服务异常，不影响独立的本地预览 |
| 程序退出 | 停止线程、释放设备并保存必要状态 |

### 13.2 日志分级

建议使用统一日志接口区分：

- DEBUG：开发诊断信息。
- INFO：设备连接、功能开关和业务流程。
- WARN：可恢复异常、截图失败和重连。
- ERROR：持久化失败、服务异常和严重运行错误。

日志不得直接输出整张图像、人脸原始数据或不必要的隐私内容。

### 13.3 日志与用户提示分离

技术日志面向定位问题；用户提示面向恢复操作。

例如：

用户提示：“截图保存失败，请检查磁盘空间或保存目录权限。”

技术日志补充：事件 ID、文件写入错误码、目标目录和失败时间。

两者可以关联，但不能用一整行内部错误路径替代用户提示。

## 14. 测试策略与验收标准

### 14.1 功能测试

| 测试项 | 通过条件 |
|---|---|
| 视频预览 | 正常显示当前帧，切换源后状态正确 |
| 暂停恢复 | 恢复后显示最新帧，不回放历史帧 |
| 人脸注册 | 有效人脸可注册，异常情况有明确提示 |
| 人脸识别 | 已注册样本可命中，未匹配样本按规则显示陌生人 |
| 档案持久化 | 重启后档案及样本仍可用 |
| 禁区绘制 | 绘制区域与实际判定区域一致 |
| 禁区持久化 | 重启后恢复已保存的禁区 |
| 遗留物检测 | 达到阈值后产生事件，移除后产生解除事件 |
| 事件冷却 | 同目标同类型事件符合规定冷却窗口 |
| 截图存证 | 开启时保存截图，关闭时仍保留事件元数据 |
| 历史查询 | 可以查看事件列表、筛选和查看详情 |
| 删除操作 | 按规则删除记录与关联文件 |
| 服务状态 | 界面与真实服务状态一致 |
| 设备异常 | 拔插、占用、断流均有明确反馈 |

### 14.2 性能测试

分别执行：

1. 仅预览基线测试。
2. 仅开启人脸检测与识别。
3. 逐项开启遗留物和禁区检测。
4. 所有识别能力同时开启。
5. 窗口缩放及视频尺寸变化测试。
6. 2 小时连续运行。
7. 24 小时长稳测试。

每项记录：

- CPU 与内存。
- 实际采集帧率。
- 实际渲染帧率。
- 分析频率。
- 单帧分析耗时及 P95。
- 帧龄。
- 事件数量与存储异常数量。

### 14.3 数据可靠性测试

- 注册后重启。
- 多次追加人脸样本后重启。
- 删除档案后重启。
- 事件产生后重启。
- 人为制造截图路径不可写。
- 模拟磁盘空间不足。
- 模拟配置文件损坏。
- 验证数据清理后没有无法管理的孤立文件。

### 14.4 隐私验收

- 首次注册告知可以正常展示。
- 用户取消后不入库。
- 删除单个档案后对应生物数据不再可用。
- 清除全部生物数据后不存在残留的档案与特征文件。
- 日志中不包含人脸图像本体。
- 未启用网络功能时，不因本地识别而向外发送人脸数据。

### 14.5 发布门禁

以下条件全部满足后，才能将对应版本标记为已验收：

- Release 构建通过。
- 核心功能测试通过。
- 性能指标有实际测量数据。
- 数据持久化和删除测试通过。
- 设备异常恢复路径通过。
- 事件与截图能够对应。
- 不存在阻塞核心流程的已知严重问题。
- 文档、版本标签与实际代码状态一致。

## 18. 产品完成定义

智能安防监控系统的核心完成标准，不是界面上出现了识别框，也不是某一次识别成功，而是以下流程能够持续、稳定、可验证地运行：

**视频源在线 → 预览实时 → 识别执行 → 规则判定 → 正确标注 → 事件生成 → 截图存证 → 历史可查 → 数据可管理。**

其中任何环节失败，都必须提供明确反馈，并且不能无故破坏其他独立能力。例如，截图保存失败不能阻断视频预览；识别关闭不能导致摄像头停止；服务未启动不能被显示为服务正常。

当前版本优先完成单机 USB 摄像头的可靠闭环，再逐步扩展视频源和远程协同能力。

**最终交付原则：先保证每条告警有明确语义、每条事件可追溯、每份档案可持久化、每种异常可恢复，再扩大硬件与平台范围。**
