## 一、总体结论

1. **套件已不是四个独立小工具**，而是初步形成「算法库 → 业务宿主 → 独立服务层 → 多端客户端」分层结构的机器视觉系统。
2. **当前最值得做的不是加功能，而是收敛**：消除资产风险、冻结通信契约、完成真实环境验收、跑通跨端闭环。
3. 四个标准必须区分：**代码结构完成 ≠ 功能链路打通 ≠ 真实环境验收通过 ≠ 产品交付成熟**。四模块分别停在不同的标准线上。

|---|---|---|---|---|---|

## 二、评估判断 vs 代码实况校准表

外部评估基于探查报告写成，以下逐项用源码核实后的结论（本次体检的关键增量）：

| # | 评估提出的问题 | 代码实况 | 结论 |
|---|---|---|---|
| 1 | 事件 ID 重启后是否仍唯一 | EventStore 用 `e<ts>-<seq>`，ts 为 epoch 毫秒，重启后 ts 必然不同；seq 持久化兜底同毫秒碰撞 | ✅ 已解决（v0.2.1 契约 A5） |
| 2 | 事件↔截图可追溯 | 事件搭车截图：落盘的正是判定当帧的标注图，精确关联 | ✅ 已存在 |
| 3 | 分析结果缺时间戳/帧序号 | `AnalysisResult` 仅有 `processMs/analysisFps`，无帧采集时间戳、无帧序号；事件 ts 取 `detectEvents` 判定时刻而非采集时刻，存在「单帧分析耗时」级偏差 | ✅ 2026-10-18 补齐（captureTsMs/frameVersion 透传，事件 ts=采集时刻，HTTP/WS/JSONL 同源） |
| 4 | 帧覆盖率不可见（覆盖式单槽丢帧无感知） | FrameBank 已有 `_version` 递增号与 `ageMs()`，但**无丢弃计数**，「画面流畅 ≠ 帧都被分析」盲区属实 | ⚠️ **真缺口**（基础设施已备，加丢弃计数 + HUD 透出即可）→ 阶段 02 |
| 5 | 跨 DLL STL 对象 ABI 风险 | 四仓同链 MinGW 8.1 + 同版本 Qt/OpenCV，MediaLink 与宿主同编译器构建 | ✅ 现状安全；需固化为构建约束（见 §8.3） |
| 6 | 原始流 vs 呈现流语义未定义 | MediaLink v0.2.1 契约 §4 已定义流内容语义，`Stream/annotated` 双模式 | ✅ 已解决 |
| 7 | 缺统一聚合健康语义 | 现状「HTTP status + stream 五态 + ws_port」三段拼接，客户端需自行推导整体健康 | ✅ 2026-10-18 解决（v0.3.0：HealthState 推导 + providers_ready，契约 minor 演进） |
| 8 | pyCore--standard/qmzy 历史原型 | 确认为 2022 Python 原型，C++ 工程零引用；face_dataset 等被 git 跟踪 | ✅ 2026-10-18 已归档（见 §8.1） |
| 9 | 阈值 ≠ 准确率（FAR/FRR 未测） | known=55%/minFace=60px 仅是配置；无独立测试集测过 FAR/FRR | ⚠️ 成立 → 阶段 05 前置认知，门禁不可宣称安全等级 |
| 10 | 模拟开门 ≠ 真实开门 | SerialGate 模拟模式与真实模式已区分 API（`isSimulated()`），但 UI 呈现未做显著区分 | ✅ 2026-10-18 解决（顶部橙/绿徽标 + 横幅"模拟放行"；串口协议 gate.ini 可配置） |

## 三、整体架构与职责边界

```
┌─────────────────────────────────────────────────────┐
│  客户端层（阶段 04-05）：Vue3 Web / 响应式移动端        │
│  实时画面 · 识别结果 · 历史事件 · 设备状态 · 基础控制   │
└──────────────────────┬──────────────────────────────┘
                       │ 《客户端接入契约》v0.2.1（唯一依赖）
┌──────────────────────▼──────────────────────────────┐
│  MediaLink v0.2.1 —— 独立服务层（纯 STL DLL，无 Qt）   │
│  HTTP :8080 只读四端点 · WS :8081 事件广播            │
│  ffmpeg 管道 → MediaMTX → WHEP/HLS                   │
└──────────┬───────────────────────┬──────────────────┘
           │ Provider 回调          │（FaceGate 接入排阶段 05）
┌──────────▼──────────┐  ┌─────────▼─────────────────┐
│ SmartSurveillance   │  │ FaceGate v0.1             │
│ 监控·分析·告警·事件   │  │ 档案·权限·签到·继电器      │
└──────────┬──────────┘  └─────────┬─────────────────┘
           │      共用算法底座       │
┌──────────▼───────────────────────▼─────────────────┐
│  FaceAlgorithm v1.0 —— 可插拔人脸算法库 DLL          │
│  HAAR + 网格直方图 LBPH · Pimpl · 接口内互斥          │
└─────────────────────────────────────────────────────┘
```

### 三条必须保持的边界

1. **FaceAlgorithm 是算法能力核心，不是系统唯一核心**。它只回答「这是谁」，不判断「能不能进门」「要不要告警」——业务规则分别在两个宿主（冷却表 / 权限四档）。
2. **MediaLink 是统一外部接入边界**。客户端只依赖契约，不得依赖 Qt 信号槽、OpenCV 内部类型、宿主业务类。三通道（HTTP/WS/媒体）要升级为完整服务接口，还需补齐：统一事件标识、聚合健康语义、连接恢复策略、错误语义（→ 阶段 03）。
3. **两个宿主共用底座但不强行合并**。监控（低延迟、误报率、恢复能力）与门禁（识别可靠性、权限正确性、设备安全）是两类业务，共享算法库与线程模式即可，业务模型各自独立。

### 统一接口 ≠ 零成本换算法

HAAR+LBPH 换 MTCNN+ArcFace 时，检测器输入、特征表示、相似度定义、阈值标定、模型格式均有差异。现接口是稳定业务边界，但替换时仍需：适配器调整 + 注册数据迁移机制（→ §8.4 模型版本化）。

- 纪律：**不用宽泛 gitignore 掩盖问题**——区分「应提交源码/应忽略缓存/应归档历史/应保留数据说明」四类

### 8.2 文档与实现同步纪律

- 契约版本必须与 DLL 实际一致；文档描述的接口必须有实现与测试证据
- 计划功能不得写成已交付；每次发布的验收记录关联 Git commit、契约版本、测试结果
- 本文档与《工作台文档记录.md》《PRD》构成三层：取舍依据 / 进度台账 / 产品基线

### 8.3 跨 DLL ABI 约束（现状安全，固化防回归）

- 四仓必须保持同编译器（MinGW 8.1）+ 同运行库 + 同版本 Qt/OpenCV
- MediaLink 纯 STL 接口减少 Qt 耦合，但**不自动保证跨工具链 ABI 稳定**；公共接口跨 DLL 传 STL 对象的前提是同链构建
- 任何一环升级工具链，四仓同步升级并全量回归

### 8.4 模型与注册数据版本化（阶段 05 前完成设计）

- 算法接口稳定 ≠ 注册样本/模型文件/阈值可跨算法版本复用
- LBPH → ArcFace 迁移时需明确：哪些数据可迁移、哪些必须重新注册
- 模型文件写入版本头；PersonStore 档案与算法模型版本解耦
